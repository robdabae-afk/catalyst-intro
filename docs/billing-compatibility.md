PR34 compatibility deployment contract

This branch changes code only. No production SQL, Stripe mutations, merges or publishes were performed.

Configure STRIPE_MODE explicitly as test or live, with matching STRIPE_SECRET_KEY_V2 and STRIPE_WEBHOOK_SECRET_V2. Do not replace legacy STRIPE_SECRET_KEY or STRIPE_WEBHOOK_SECRET. Keep the old stripe-webhook deployed unchanged. Its subscriptions/token grants continue to use the original Stripe account. New checkout fails closed if a saved legacy customer cannot be retrieved in the V2 account, or if identities conflict. Legacy-only portal uses the original key. Existing customers are reused, never overwritten. Both checkout adapters reject existing active/incomplete canonical subscriptions; pending V2 checkout also has a unique database order guard.

Wallet policy is dynamic, not a conversion migration. One purchased V2 credit buys one instant message. Thirty legacy tokens buy one instant message because the old endpoint cost is exactly 30. Displayed message credits = V2 credits + floor(max(tokens,0)/30). Tokens are not copied, reset or rounded. A debit consumes one V2 credit first, otherwise inserts a 30-token spend into the original transaction ledger under a locked profiles row. For example 65 tokens show two message credits and a remainder of five; after two sends the five remain usable for other legacy token services. This is not a claim that one token equals one credit. Legacy Pro monthly token grants are preserved, not converted into extra V2 grants.

Deploy the compatibility SQL and send-instant-message adapter together before enabling new purchases. The adapter retains the old instant_messages inbox and response shape; V2 sends retain messages/matches. Shared billing_instant_sends idempotency and shared locked balance prevent either endpoint reusing the same balance. Old clients without requestId cannot deduplicate network retries; each call remains a distinct send. Before adapter deployment a warm old edge worker uses separate transaction+message writes, so its spend can still need refund on insert failure. Drain old workers before activation. The replaced token balance trigger prevents negative balances from those workers, but does not make their two separate HTTP writes atomic.

The billing_rollout_flags row defaults enforce_v2=false. Restrictive swipe incoming reads, match/message policies, match reopen restriction and daily swipe limit remain disabled for cached clients until new frontend and adapters are published. Enable only afterwards with explicit approved SQL updating that singleton flag. The existing approval rules remain intact. Both pair orientations are accepted; inserts use pair locks and avoid creating new canonical duplicates. Existing duplicate historical rows are retained, not rewritten. Cached direct-match inserts encountering a duplicate are suppressed, so clients relying on insert.single may need to reread the existing pair.

Legacy active profiles.subscription_status with future expiry and new provider entitlements both count as Pro. All useSubscription readers use the unified snapshot with a pre-migration legacy fallback. Stripe management availability and expiry are derived, not hardcoded.

The fixture models the legacy schema contract, not a full staging Supabase clone. Full-schema staging, portal/account mismatch integration, cached real-browser clients and hosted Checkout/webhook end-to-end must still be exercised after this compatibility change. Previous hosted tests predate this patch. Restrictive token ledger INSERT/UPDATE/DELETE policies and an invoker profile balance trigger block authenticated non-admin token minting independently of rollout. Trusted SECURITY DEFINER debits and service-role/admin grants remain supported. Direct mint and ledger mint rejection are exercised locally. Audit additional historic balance-grant RPCs before enabling payments. Existing cross-account legacy active users cannot buy V2 until account strategy is resolved; they keep access and original-account servicing.

Local checks passed npm typecheck, production build, all 64 Bun tests, Deno check for four changed endpoints, Deno mode test, original SQL entitlement/annual/idempotency assertions, compatibility SQL and an actual concurrent legacy/new debit with only one successful send from a 30-token balance. Build retains the pre-existing large-chunk advisory.
